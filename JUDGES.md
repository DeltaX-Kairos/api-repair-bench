# Judge path: repair the client that dropped page two

For integration engineers fixing API clients that return HTTP 200 but silently lose or corrupt data.

## One task, one result to inspect

1. Open the [live workspace](https://repairbench.deltaxevaluate.com/live/).
2. Choose **Pagination repair**. The broken client returns the first page without following its `next` cursor. The [fictional incident](docs/incident.md) states the expected behavior.
3. Click **Run live repair** once when admission is available.
4. Watch **NVIDIA Nemotron**, via **Nebius Token Factory**, propose a replacement and **Nebius Sandbox** execute the declared checks.
5. Inspect the generated function, named check results and stopping reason. A completed initial failure may receive one correction; a passing proposal or completed correction stops the workflow.
6. Select **Download evidence**. Review and export do not merge or deploy code.

A fresh run can pass, fail, be rejected before execution or stop with an infrastructure/uncertain result. None is relabelled as a successful repair. The exact outcome belongs to that run's contract and proposal.

## What the control architecture enforces

Model output has proposal authority only. Application code binds the contract, source and evaluation artifacts; controls remote dispatch and comparison eligibility; and permits a finite correction protocol. Candidate execution is remote, while final comparison is external. The observation runner still shares the candidate process, so passing checks do not establish independently attested execution.

The [README architecture section](README.md#architecture-proposal-authority-without-deployment-authority) details the controls, failure taxonomy and next execution-attestation gate. [Usability validation](docs/usability-study.md) is a prepared protocol, not completed research.
